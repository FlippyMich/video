# BloomStudio

A browser-based 3D animation studio for making bright, friendly videos for
children — and the film it was built to produce, *Buzzy's Sense-ational
Adventure!*

Everything runs in the browser on WebGL. There are no model files, no texture
downloads and no server: characters, props and sets are generated from code, so
the whole cast is available the instant the page loads and a project file is a
few megabytes of plain JSON.

## Running the studio

```bash
npm install
npm run dev          # http://localhost:5173
```

Then either poke at the film it opens on, or go to **Script**, type some
dialogue and press **Build the film**.

`npm run build` produces a static `dist/` you can host anywhere; there is no
back end.

## The idea

Most 3D tools ask you to build a world before you can tell a story. This one
inverts that: you write what happens, and the studio works out the rest.

```
# Title: A Very Good Morning

## Scene: The garden | theme=garden time=morning

[Buzzy flies in and waves]
BUZZY (excited): Good morning, everybody! It's me, Buzzy!
?? Can you wave back? | 3s | hand-icon | Hello!
LILY (happy): Morning, Buzzy! What shall we do today?
@sfx: sparkle
```

That is a complete input. From it the studio casts the characters, places them
on a shallow arc facing the camera, generates the performance (a wave, a nod, an
idle sway, blinking), works out the lip-sync, chooses and cuts the cameras,
places the sound cue, writes the captions, and builds the audience beat with an
on-screen prompt and a look down the lens.

Everything it produces is ordinary editable data afterwards. There is no "script
mode" to be stuck in — the auto-animator writes keyframes, and you drag them
like any others.

## Making the film

The pipeline turns the script into every delivered file. Each stage is
independent and re-runnable:

```bash
node pipeline/01-voice.mjs      # record every line, derive lip-sync
node pipeline/02-project.mjs    # build the film using the real voice timings
python3 pipeline/04-audio.py    # synthesise music and sound effects
node pipeline/03-render.mjs     # render the master (about an hour)
node pipeline/03-render.mjs --green   # the green-screen version
node pipeline/05-mix.mjs        # stems, ducking, final mix
node pipeline/06-exports.mjs    # captions, glTF scenes, shot list, cue sheet
node pipeline/07-script-doc.mjs # the timestamped script as .docx
bash pipeline/run-all.sh        # all of the above, in order
```

Stage 3 drives a headless browser frame by frame and pipes JPEGs straight into
ffmpeg — nothing touches the disk in between, which matters when a
seven-minute film is fourteen thousand frames.

**Prerequisites for the pipeline** (not for the studio): `ffmpeg`,
`espeak-ng`, Python with `numpy` and `scipy`, and Playwright's Chromium.

## About the voice track

The voices in the delivered film are **synthesised with espeak-ng**. They are
clear, correctly timed and precisely lip-synced, and they are a *scratch track*
— a formant synthesiser, not a performance. The film is delivered this way so
that everything else about it is finished and reviewable.

Replacing them is a first-class path, not a rewrite:

1. Record each line as its own file into `deliverables/audio/vo/`, keeping the
   existing filenames.
2. Re-run from stage 2. The studio measures each recording, retimes the cut
   around the performance, and rebuilds the mouth shapes from the new audio.

`docs/knowledge-base/replacing-the-voice-track.md` has the detail.

The music and sound effects are **not** placeholders — they are generated by the
synthesiser in `pipeline/lib/synth.py` and are yours to use.

## Working with other people

```bash
node server/collab.mjs          # ws://localhost:8787
```

Then **Collaborate** in the top bar: enter the server, pick a room name, and
share it. The first person in brings the film; everyone who joins receives it.
Edits are shared as they happen, and you can see who else is there.

It resolves conflicts at entity level — a scene, a shot — with last-writer-wins.
If two people change the *same* scene at the same moment, the later change wins
and the earlier one is lost. It is not a CRDT, the interface says so, and in
practice dividing the work by scene avoids it entirely.

The relay stores nothing. Rooms exist while somebody is in them.

## Bringing in outside assets

**Library → Characters or Props → Bring in your own.**

- **Models** — glTF (`.glb` / `.gltf`) from TurboSquid, Sketchfab, Poly Haven,
  Kenney and so on. Scaled to a sensible height and stood on the ground on
  import. They keep their own materials, so they will not match the house toon
  style — usually fine on a background prop, obvious on anything in the
  foreground.
- **Animation** — Mixamo, Rigify or VRM skeletons. Retargeting takes rotations
  only: a Mixamo character is roughly seven heads tall and these are two to four,
  and copying joint *positions* onto that would dislocate every limb. Retargeted
  motion lands on the normal timeline, so you can layer a wave on top of an
  imported walk.

Anything you import stays under its own licence.

## How the engine is put together

```
src/engine/
  types.ts            the project document — one plain-JSON object per film
  rig/                seven rig families, a ten-shape viseme set, twelve expressions
  anim/               keyframe evaluation and 36 procedural action clips
  assets/             characters, props, environments, materials, 3D text
  fx/                 deterministic particle systems, cloth, rope and rigid bodies
  script/             the script parser and the auto-animator
  render/             the virtual director, the player, exporters
  collab/             the real-time session
  workers/            script building, off the main thread
  scene-builder.ts    turns a scene document into a live three.js scene
```

A few decisions worth knowing about:

**One renderer.** The editor preview, the in-browser export and the production
pipeline all call the same `Player.render(t)`. The preview cannot drift from the
delivered file because they are the same function.

**Animation is a pure function of time.** Nothing accumulates frame to frame, so
scrubbing backwards is exact, particle effects are reproducible, and the
headless render produces the same pixels as the preview.

**Nothing is a binary asset.** Characters and sets are built from primitives at
load time. That keeps the library instant and offline, makes every character a
readable function rather than an opaque file, and means a whole film fits in a
JSON file you can email.

**Sets are seeded, not built.** A garden is generated from a theme and a number.
The same seed always gives the same garden, which is what makes "shuffle until
you like it" a safe button to press.

**Even the physics is deterministic.** Cloth and bouncing bodies use Verlet
integration run from `t = 0` at a fixed step, and a backwards seek re-simulates
rather than reversing. A solver that accumulated state would break scrubbing and
make every export subtly different from the last.

## Deliverables

Produced by the pipeline into `deliverables/`:

```
video/      the master, and a green-screen version
audio/      voiceover / music / sfx stems, the full mix, and every source cue
captions/   .srt, .vtt and a styled .ass for burn-in
blender/    one .glb per scene with baked animation and camera, plus an importer
documents/  the timestamped script (.docx), shot list and cue sheet (.csv)
```

`deliverables/README.md` describes each file and what it is for.

## Attribution and reuse

Everything in this repository — characters, sets, music, sound effects, the
script — was generated for this project. There are no third-party assets, no
sample libraries and no fonts to license.

The visual style is an original design in the general idiom of preschool 3D
animation. If you are producing under an existing brand, swap
`src/engine/assets/palette.ts` and add your own character builders; the rest of
the studio does not care what the cast looks like.
